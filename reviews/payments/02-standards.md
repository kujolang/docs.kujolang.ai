# External standards and provider findings

Sources were retrieved September 12, 2026. Publication/release dates are distinct from retrieval dates. Living pages and SDK source describe current behavior, not contractual server guarantees. “Open standard” is a project's description unless an actual standards body status is established.

## Released foundations and evolving protocol specifications

| Publisher / exact source | Version or maturity | Finding and architectural consequence |
|---|---|---|
| IETF Datatracker, [Payment HTTP authentication](https://datatracker.ietf.org/doc/draft-ryan-httpauth-payment/) | `draft-ryan-httpauth-payment-01`, Internet-Draft, not an RFC | Defines Payment challenge/credential authentication. A protocol adapter pins the supported revision. Kujo does not replace the wire protocol or mistake draft publication for security certification. |
| UCP, [overview snapshot](https://ucp.dev/2026-08-25/specification/overview/) | Date-versioned 2026-08-25 project specification | Capability negotiation, merchant/platform/payment-provider roles and payment handlers support multiple transports. Map UCP checkout/handler terms into a prepared purchase; do not import its cart, catalog, orders and fulfillment model into core. |
| ACP maintainers, [repository](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol) | README calls ACP beta; latest stable snapshot directory 2026-04-17; separate unreleased development | ACP supports programmatic commerce with versioned schemas. Released snapshot is not universal deployment. Preserve merchant control and use exact dated contracts. |
| ACP, [delegated payment schema](https://github.com/agentic-commerce-protocol/agentic-commerce-protocol/blob/main/spec/2026-04-17/openapi/openapi.delegate_payment.yaml) | 2026-04-17 schema | Delegation is a distinct credential/allowance API, not a safe model-facing operation by default. Keep credential formats in the backend. Payment authorization can map to allowance/merchant/expiry without copying card fields upward. |
| AP2, [specification](https://ap2-protocol.org/ap2/specification/) and [security considerations](https://ap2-protocol.org/ap2/security_and_privacy_considerations/) | Current v0.2 documentation; standardization is ongoing, not completed FIDO certification | Open/closed Checkout and Payment Mandates distinguish constraints from exact final authorization. Signed mandates need issuer/key trust, verifier checks and replay prevention. They are a possible evidence adapter; V1 does not mint speculative AP2 mandates. |
| MCP, [elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation) | 2025-11-25 protocol snapshot | URL-mode interaction lets sensitive human authorization occur outside ordinary tool inputs. Completion notification is not payment evidence. Use trusted application action refs and independently observe authority; never keep a payment invocation waiting on a human. |
| Coinbase, [how x402 works](https://docs.cdp.coinbase.com/x402/how-it-works) | Living protocol implementation documentation | Price/recipient/method negotiation, signed payment, verification and settlement are distinct stages; facilitator role is optional protocol infrastructure. A machine-payment backend fits without making core a cryptocurrency wallet. Fiat V1 must not relabel arbitrary crypto assets as currency. |
| Coinbase, [x402 FAQ](https://docs.cdp.coinbase.com/x402/support/faq) | Living implementation documentation | Payment identifiers can provide idempotency extensions. Support depends on the actual server/facilitator combination; a protocol name alone cannot establish duplicate protection. |

## MPP protocol and implementations

| Source | Evidence | Consequence |
|---|---|---|
| MPP, [protocol index](https://mpp.dev/llms.txt) | Current method/transport/SDK index, including charge, session and subscription intents | Restrict V1 to one charge. Avoid global fetch patching that automatically purchases every 402 resource. |
| MPP, [credentials](https://mpp.dev/protocol/credentials) | Credentials echo the challenge, carry method-specific proof, and require method-specific replay checks separately from challenge integrity | Keep proof material inside the executor. Validate challenge, recipient and exact request, and require replay controls; merely signing terms does not consume authority. |
| MPP, [receipts](https://mpp.dev/protocol/receipts) | Payment-Receipt is an optional server acknowledgment with method/reference/status/time | A missing receipt is possible; HTTP success without independently correlated payment evidence cannot satisfy Kujo's success rule. A malicious merchant can make a false acknowledgment. |
| MPP, [Stripe charge method](https://mpp.dev/payment-methods/stripe/charge) | SPT-backed charge route; server derives authorized amount/currency/recipient/expiry from its own records | Link wallet plus merchant MPP route is a composed backend. Do not trust a client-supplied amount or thin proxy to establish authority. |
| MPP, [MCP transport](https://mpp.dev/protocol/transports/mcp) | JSON-RPC payment challenges and credential/receipt metadata transport | Credential-bearing MCP transport must run inside the executor. MCP metadata is a data channel, not an isolation guarantee. Disable automatic replacement-challenge payment retries after uncertain outcomes. |
| Stripe, [MPP announcement](https://stripe.com/blog/machine-payments-protocol) | Product announcement, distinct from normative protocol text | Establishes investment and use case; does not establish settlement guarantees or mandate a Stripe dependency in core. |

## Security applicability and announcements

PCI SSC distinguishes [issuer/virtual-card tokens from EMV payment tokens](https://www.pcisecuritystandards.org/faqs/1384/). Those categories cannot be collapsed into “tokenized means out of scope.” PCI SSC also states that [sensitive authentication data must not be stored after authorization](https://www.pcisecuritystandards.org/faqs/1533/) even without PAN present. A future raw-card executor changes the data-handling environment and needs deployment-specific PCI assessment. This review neither determines compliance nor claims an exemption for SPT/LPT.

[Link's product page](https://link.com/agents) labels granular controls, additional payment methods and saved preferences as coming soon. The [AP2 home page](https://ap2-protocol.org/) describes ongoing standardization work and v0.2 materials. Neither future product control nor future certification is a prerequisite for V1. No social post was used as a technical specification.

## Evidence limits

The web extractor could not read several official Markdown responses; direct HTTPS retrieval succeeded. [External fetch manifest](evidence/external-fetches.json) records URLs, response hashes and byte counts; temporary source bodies are not bundled. [Pinned Link manifest](evidence/link-source.json) records source revision and individual file hashes. SDK sources were inspected without installing, authenticating or running Link commands.

Server idempotency retention, consistency delay, exact financial finality and recoverability after a lost create/charge response are **not established** by these sources. The architecture resolves this uncertainty by refusing unsupported live routes, allowing explicit unknown status and prohibiting automatic resubmission. A Link backend can be implemented against fixtures now; promoting it to real-money use requires the stated independent correlation and deployment gates.
