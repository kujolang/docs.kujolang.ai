## Conflicts, limitations and interpretation

The direct Link repository is newer than indexed snippets: it lists LPT and its SDK includes `payment_status_details`, `link_transaction_id` and a transactions resource. These improve the reconciliation hypothesis, but source types do not establish provider consistency guarantees, visibility latency or terminal finality. Link's server implementation was unavailable; no account or live transaction was used.

The general SPT issuing API and Link-issued SPT flow are distinct. The former documents a Stripe profile and issued-token API; the latter uses Link wallet authorization and SpendRequests. Access to one must not be assumed to grant access to the other. Link's README publishes fixed limits while its user-info API returns account limits. Treat limits as dated observations with a short cache lifetime, then revalidate before execution.

The MPP documentation returned a content-type error through the web extractor; the same official pages were retrieved over HTTPS and their HTML text inspected. No mirror or social source substitutes for the specification. A merchant receipt can acknowledge payment, but authenticated processor evidence determines the adapter's financial conclusion.

Stable foundations are exact-money arithmetic, authenticated authorization, isolation and durable uncertain-outcome handling. ACP/UCP are released project specifications; AP2 and MPP continue evolving; Stripe preview APIs and Link behavior are provider-specific. Announced granular controls or future wallet features are not V1 dependencies.
